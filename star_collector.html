Star Collector

A p5.js arcade sketch rebuilt to show what optimizing a game loop actually looks like.

Play

Score 0 · Time 60s · Combo ×1 · Best 0

How to play

  • Move: ← ↑ → ↓ or W A S D, or drag anywhere on the playfield.
  • Start / restart: Enter or the Start button.
  • Pause: P or Space. The game also pauses itself if you switch tabs.
  • Scoring: collect stars for 60 seconds. Pickups within 1.6 seconds of each other raise the multiplier to a maximum of ×5.
What each object does. Every object is told apart by shape as well as colour.
Object Shape Effect
Star Small white circle 1 point × combo
Gold star Large spinning five-point star 5 points × combo
Asteroid Lumpy tumbling rock Costs 3 seconds and resets the combo

What changed from the original sketch

The starting point was the standard classroom sketch: a player circle, fifty star circles, and a collision check inside draw(). Everything below is commented in place in the sketch source, js/star_collector.js.

Bugs that were fixed

  1. Removing while looping forward. stars.splice(i, 1) inside a for loop shifts every later star down one index, so the star immediately after a collected one is skipped that frame. This version recycles stars instead of removing them, so the array length never changes.
  2. The game emptied out. Collected stars were gone forever; after about a minute there was nothing left to play with. Stars are now returned to the bottom of the screen with a fresh type, size and speed.
  3. Diagonals were faster. Holding two arrow keys moved the player 5 pixels on each axis — about 7.07 pixels of travel, 41% faster than a straight line. Diagonal input is now scaled by 1 / √2.
  4. The player could leave the canvas. Position is clamped with constrain().
  5. Stars popped into view. Respawning at y = height made the top half of a star appear instantly; respawning below the edge lets it slide in.

Performance work

  • No square roots in collision. dist() computes a square root that is then thrown away by a comparison. Comparing squared distances against a cached squared radius gives the same answer for less work.
  • Object pooling. Stars and particles are allocated once at startup and reused. Nothing calls new during play, so the garbage collector has no reason to interrupt a frame.
  • Frame-rate independence. Speeds are in pixels per second and multiplied by deltaTime, so the game plays the same on a 30 Hz laptop and a 144 Hz monitor. The delta is clamped so a backgrounded tab cannot resume and teleport everything off screen.
  • Pre-rendered background. The gradient and 220 dust specks are drawn once into an off-screen p5.Graphics buffer and blitted with a single image() call each frame.
  • Batched fills. Changing fill colour is the expensive part of a 2D canvas draw, so the sketch loops the star array three times — once per colour — instead of calling fill() once per object. Particles fade by shrinking rather than by changing alpha, for the same reason.
  • Precomputed geometry. The ten vertices of the gold star are computed once at load time, not every frame.
  • Lower pixel density. pixelDensity(1) avoids drawing four to nine times as many pixels on a high-DPI display.

Accessibility work

  • The score, timer and combo are mirrored as real text below the canvas, because canvas pixels are invisible to a screen reader.
  • Round start, pause, countdown milestones and the final score are announced through a polite live region — meaningful moments only, not every frame.
  • Object types are distinguished by shape as well as colour, and the timer is shown as a number as well as a coloured bar.
  • Only the four movement keys have their default behaviour suppressed, so Tab and browser shortcuts keep working — there is no keyboard trap.
  • Decorative motion (particles, pulsing, screen shake) is switched off when the operating system asks for reduced motion. Motion the game depends on stays.

Try it yourself

Open js/star_collector.js and change one constant at a time — STAR_COUNT, PLAYER_SPEED, ROUND_SECONDS, or a row of the KINDS table. Adding a fourth kind of object means adding one row to that table and one drawing pass; that is the point of storing the rules as data rather than as branching code.
